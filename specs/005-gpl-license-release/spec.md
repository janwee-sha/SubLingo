# 功能规格：GPL 许可与 v0.1.0 重发

**功能目录**：`005-gpl-license-release`

**创建日期**：2026-08-14

**状态**：已批准

**输入**：为 SubLingo 添加 GPL-3.0 License，在 README 顶部按参考项目样式添加许可链接，并重新发布包含许可证的远程 GitHub Release v0.1.0。

## 用户场景与测试

### 用户故事 1：确认项目许可（优先级：P1）

用户或贡献者访问仓库时，可以立即确认 SubLingo 只按 GPL 第 3 版授权，并从 README 直接打开完整许可文本。

**优先级理由**：没有明确许可证时，公开源码不能形成可依赖的修改与再分发授权。

**独立测试**：检查仓库根目录许可全文、包管理元数据和 README 徽章，三者均明确指向 GPL 第 3 版且不允许自动选择未来版本。

**验收场景**：

1. **假如** 用户打开根 README，**当** 查看顶部徽章，**那么** 可见 GPL v3 徽章并可打开本仓库 `LICENSE`。
2. **假如** 使用者检查仓库元数据，**当** 读取包管理清单，**那么** 获得唯一 SPDX 标识 `GPL-3.0-only`。

---

### 用户故事 2：获得合规安装包（优先级：P2）

用户下载正式安装包时，可以在归档根目录读取 SubLingo 许可证和随包第三方组件的声明。

**优先级理由**：GitHub 仓库中的许可证不能替代分发安装包自身的授权与第三方归属材料。

**独立测试**：生成安装包并审计最终归档，确认许可文件存在且所有原有敏感材料、源码和构建产物拒绝规则保持有效。

**验收场景**：

1. **假如** 发布构建成功，**当** 检查最终 `.iinaplgz`，**那么** 根目录包含 `LICENSE` 与 `THIRD_PARTY_NOTICES.txt`。
2. **假如** 任一许可文件缺失或归档包含未允许内容，**当** 执行发布审计，**那么** 发布失败且不会公开不完整安装包。

---

### 用户故事 3：替换 v0.1.0 正式发布（优先级：P3）

维护者可以用当前提交重建同版本安装包，并通过受控的一次性流程把远程 v0.1.0 替换为包含许可证的版本。

**优先级理由**：已公开的不含许可证安装包需要修正，同时替换必须限制目标、保留审计并避免误改其他版本。

**独立测试**：从已知旧 tag 和旧包哈希开始执行一次性流程，确认新 Release、tag、正文、资产与触发提交一致；在前置状态不匹配时确认流程无写入失败。

**验收场景**：

1. **假如** 远程 v0.1.0 的 tag 与旧安装包都匹配已记录身份，**当** 新包通过全部门禁，**那么** 远程 Release 被当前提交的新包、校验文件和审计正文替换并保持 Latest。
2. **假如** 旧 tag、旧安装包哈希或版本任一不匹配，**当** 流程运行，**那么** 替换在删除任何远程状态前失败。
3. **假如** 替换已成功，**当** 后续普通 main 提交触发发布，**那么** 已发布的稳定 v0.1.0 保持只读且不会再次被替换。

### 边界情况

- 已存在同名 Release 但为 prerelease、重复 Release 或使用不同 tag 目标时，替换必须拒绝。
- 旧 Release 含有未记录的额外资产、缺少安装包或资产下载后哈希不符时，替换必须拒绝。
- 新包审计、上传或最终远程状态核验失败时，不得把不完整 Release 报告为发布成功。
- GitHub 图形界面安装、卸载和实际播放无法由 CI 证明，必须继续标记为未覆盖。

## 需求

### 功能需求

- **FR-001**：仓库 MUST 包含未经改写的 GNU General Public License version 3 标准全文，并以 `GPL-3.0-only` 作为项目 SPDX 标识。
- **FR-002**：根 README MUST 在顶部使用参考项目的 `for-the-badge` GPL v3 徽章样式，并链接本仓库 `LICENSE`。
- **FR-003**：正式安装包 MUST 在根目录包含项目 `LICENSE` 与 `THIRD_PARTY_NOTICES.txt`，后者 MUST 保留随包运行依赖的版权与许可证文本。
- **FR-004**：打包、包校验与最终归档审计 MUST 把两份许可文件作为必需项，并继续拒绝现有禁止内容、不安全路径、符号链接和加密条目。
- **FR-005**：v0.1.0 替换 MUST 仅在旧 tag 指向 `ef15570911d180c139e77f5d38dc0a5169ba4235` 且旧安装包 SHA-256 为 `4b023319072a48a47fff13c77e9c838c087bc32f1aaea68bd48dd1daf2d15b13` 时允许执行。
- **FR-006**：替换 MUST 使用通过八项发布门禁和最终归档审计的新安装包，并将新 tag 精确指向触发提交。
- **FR-007**：替换后的 Release MUST 为公开、非 prerelease、Latest，并只发布当前审计正文，不额外添加替换历史说明。
- **FR-008**：一次性替换能力 MUST 在成功发布后从默认发布路径移除；普通已发布稳定版本继续只读跳过。
- **FR-009**：失败流程 MUST 保留或恢复可用的远程 v0.1.0；不得留下被报告为成功的半成品状态。
- **FR-010**：变更 MUST NOT 改变插件运行时、权限、字幕数据流、翻译行为或版本号 `0.1.0`。

### 关键实体

- **项目许可**：标准 GPL v3 文本、固定 SPDX 标识和 README 入口。
- **第三方声明**：随安装包分发的运行依赖名称、版本、版权和许可证全文。
- **旧发布身份**：旧 tag commit、旧安装包名称与 SHA-256，用于替换前的失败关闭校验。
- **新发布身份**：触发 commit、包内版本、归档名称、大小、SHA-256、审计清单和远程发布状态。

## 成功标准

### 可衡量结果

- **SC-001**：仓库中的许可全文、README 徽章目标、`package.json` 与锁文件根包元数据 100% 一致指向 `GPL-3.0-only`。
- **SC-002**：正式归档 100% 包含两份必需许可文件，且所有既有禁止内容审计继续通过。
- **SC-003**：八项自动化发布门禁全部通过，构建文件与包内 helper 都具备 `arm64`、`x86_64`、可执行权限和有效签名。
- **SC-004**：远程 v0.1.0 的 tag、Release 正文、两项发布资产、Latest 状态和新包 SHA-256 100% 与本次审计证据一致。
- **SC-005**：一次性替换完成后的普通发布路径对现有稳定 v0.1.0 执行只读跳过，不产生第二次替换。

## 假设

- 用户已明确选择 `GPL-3.0-only`，而不是 `GPL-3.0-or-later`。
- 用户已明确接受替换既有 v0.1.0 tag 与资产造成旧校验值失效，并要求正文不说明替换历史。
- `@noble/hashes 2.3.0` 是当前唯一进入 JavaScript 运行包、需要随包保留许可证的第三方 npm 依赖；开发依赖不进入安装包。
- 系统 libcurl 由 macOS 提供，不作为 SubLingo 安装包中的第三方二进制分发。
- IINA 图形界面宿主验收不阻塞自动正式 Release，但不能被自动化结果标记为通过。
