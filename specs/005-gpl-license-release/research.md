# 研究结论：GPL 许可与 v0.1.0 重发

## 许可证表达

**决策**：使用标准 GPL v3 全文和 SPDX `GPL-3.0-only`。

**理由**：用户已明确排除未来版本自动适用；标准 SPDX 标识可被 GitHub 和包管理工具识别。

**评估过的替代方案**：`GPL-3.0-or-later` 会扩大未来授权范围；自定义文本降低兼容性和可识别性。

## README 样式

**决策**：复用参考仓库 `License-GPLv3-blue?style=for-the-badge` shields.io 徽章，并链接 SubLingo 根 `LICENSE`。

**理由**：与用户指定样式一致，同时保持目标仓库正确。

**评估过的替代方案**：普通文字链接和 flat 徽章都不符合指定样式。

## 随包第三方声明

**决策**：`THIRD_PARTY_NOTICES.txt` 只包含实际进入运行包的 `@noble/hashes 2.3.0` MIT 版权和完整许可文本。

**理由**：开发依赖不进入安装包；libcurl 由系统动态提供，并非归档中的第三方二进制。

**评估过的替代方案**：把整个依赖锁文件或所有开发依赖许可证装入包会违反最小发布产物原则。

## 同版本替换

**决策**：使用一次性、失败关闭的 CI 替换模式；仅当旧 tag commit 与旧包哈希精确匹配时执行，成功后删除替换能力。

**理由**：当前发布器有意跳过已发布稳定版本，且默认禁止覆盖。一次性接口既能保留八项门禁和审计，又不会把可变 tag 变成长期策略。

**评估过的替代方案**：手工 UI 替换难以形成可测试契约；永久允许覆盖会破坏稳定版本身份；发布 v0.1.1 与用户明确选择不符。

## 失败处理

**决策**：所有旧状态校验在删除前完成，并把旧正文与全部旧资产下载到本次进程的临时目录；远程替换按删除旧 Release、删除旧 tag、创建当前提交 draft、上传并核验、公开的顺序执行。删除后任一步骤失败时，清理新对象，用缓存的旧正文、资产和旧 commit 重建原公开稳定 Release；只有恢复状态再次核验成功后才结束失败流程。

**理由**：预删除验证避免误删；本地临时缓存覆盖 GitHub 非事务性删除窗口，可满足失败后恢复可用公开版本的规格，同时不把旧资产写入仓库或 Actions artifact。

**评估过的替代方案**：自动重建旧二进制无法保证旧哈希一致；仅保留新 draft 会让旧公开版本暂时不可用；永久保存旧资产会增加不必要的发布材料。
