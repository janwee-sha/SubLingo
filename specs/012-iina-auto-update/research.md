# 研究：IINA 自动更新发现

## IINA 更新契约

- **决策**：在正式 `Info.json` 中增加 `ghRepo` 和 `ghVersion`，继续由 IINA 从 GitHub 最新正式 Release 获取 `.iinaplgz`。
- **理由**：IINA 1.4.4 的现有更新逻辑只在这两个字段存在时比较更新，并复用 GitHub 安装路径下载 Release 包；无需自定义更新器。
- **备选方案**：在插件内自行检查或下载更新。该方案会扩大网络、副作用和安全范围，因此拒绝。

## 默认分支兼容

- **决策**：保留 `main` 为唯一开发与发布分支，不创建 `master` 兼容分支。
- **理由**：IINA 官方插件同样使用 `main` 默认分支；实际读取验证表明 GitHub 可通过 IINA 当前请求的 legacy `master/Info.json` 路径返回默认分支内容。
- **备选方案**：维护镜像分支或修改 IINA 上游。前者引入同步状态，后者超出 SubLingo 0.3.3 范围。

## 更新序号

- **决策**：使用 `major × 1,000,000 + minor × 1,000 + patch` 生成更新序号，要求每个 SemVer 分量位于 0–999；0.3.3 对应 `3003`。
- **理由**：IINA 只要求严格递增整数。确定性映射使发布门禁能直接拒绝版本已提升但 `ghVersion` 未同步的情况，无需查询或修改历史 Release。
- **备选方案**：人工维护从 1 开始的计数。它符合 IINA 格式，但无法仅凭当前仓库状态发现遗漏。

## 旧版引导

- **决策**：明确告知 0.3.2 及更早版本需要从 GitHub 或正式包手动升级一次到 0.3.3。
- **理由**：已发布安装包没有更新字段，远端修改无法让这些本地清单开始检查更新。
- **备选方案**：声称 IINA 可直接自动升级旧版。该行为不可实现且会误导用户。

## 验证分层

- **决策**：共享生产校验模块同时服务源码发布元数据、staging 包验证和最终归档审计；测试直接调用该模块并覆盖无效身份。
- **理由**：满足宪法对生产接口验证的要求，并能证明最终交付对象没有在打包过程中丢失更新字段。
- **备选方案**：只用测试读取 `Info.json` 或只检查 README。该方案把文档和文件存在性当成契约，违反项目宪法。

## 发布范围

- **决策**：本次准备并审计 0.3.3 发布候选包，不执行 commit、push、tag 或 GitHub Release 创建。
- **理由**：版本准备与本地验证属于用户请求范围；公开发布是独立的外部写操作，需要后续明确指示。
- **备选方案**：实现完成后立即公开发布。该操作会改变远端状态，因此不自动执行。
